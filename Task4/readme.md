1. Для работы нового сервиса требуется реляционная база данных, чтобы сохранять состояние задач
2. Взаимодействие между сервисами происходит по схеме pub sub, асинхронно. Приложение core отправляет события в брокере, а сервис расчеты вычитывает оттуда данные для запуска обработки.
Получение информации core приложение получает так же через kafka.
3. Клиент в браузере же получает информацию через SSE от core приложения
4. При взаимодействии нового сервиса и страховых:
* Timeout - т.к. сервисы могут зависнуть, держать соединение, нужно настроить лимит в 5 сек чтобы не ждать вечно ответ
* Retry - если это не ошибка клиента (400 и т.д.) можно повторить запрос несколько раз по экспоненте. В пределах общего лимита конечно же
* Circuit Breaker - т.к. каждая интеграция с отдельной компанией, стоит учитывать что какие-то могут испытывать проблемы, поэтому введение такого паттерна позволить избежать лишних запросов т.к. заранее предполагаем ошибочный ответ
* Rate Limiting - в зависимости от партнера, кто-то может указывать лимиты для своего API и нужно их уважать чтобы не спамить и можно эти запросы стоят денег, а у нас есть бюджет.
5. Сервисы должны быть stateless состояние храниться в базе и подов можно сделать больше/меньше чтобы соответствовать нагрузке
